# Vasilis Xentes — professional web development

A bilingual commercial portfolio and lead-generation website for professional websites, business automation and custom web applications. Built fresh in this directory; no files or private client information from earlier projects are required. No deployment has been performed.

## Local Windows setup

Use Python 3.12+ and PowerShell from `C:\Freelance_Dev_Website`. Everything below stays in the project directory. Virtual-environment activation is optional; using its interpreter directly avoids PowerShell execution-policy issues.

```powershell
cd C:\Freelance_Dev_Website
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install --cache-dir .cache\pip -r requirements.txt
Copy-Item .env.example .env
# Edit .env privately; never commit it.
# Set SECRET_KEY to a private random value before continuing.
.\.venv\Scripts\python.exe -m flask --app wsgi db upgrade
.\.venv\Scripts\python.exe -m flask --app wsgi seed-dev
.\.venv\Scripts\python.exe -m flask --app wsgi run
```

Open `http://127.0.0.1:5000`. The first public visit offers Ελληνικά / English. The EL | EN switch remains in navigation. Admin pages have no language gate.

Alternatively, start local Windows development with `.\.venv\Scripts\python.exe run.py`.

`SECRET_KEY` is intentionally blank in the example. The application refuses startup without an environment-supplied key, including in development. Before normal local use, set your own stable random key in your private `.env`; do not use a published example key. No real secret file is included or generated by the setup commands above beyond copying blank placeholders.

Development-only admin at `/admin/login`:

- Username: `dev-admin`
- Password: `dev-only-change-before-launch`

`seed-dev` is idempotent and refuses production mode; production login also rejects the `dev-admin` account. These public credentials must never be used on an internet-accessible deployment. Use a fresh production database and `flask --app wsgi create-admin`; the password prompt is hidden and requires at least 16 characters. Do not pass production passwords as command arguments or reuse the development database.

## Architecture

- `app.create_app()` configures extensions and public/admin blueprints.
- SQLAlchemy models use portable types; SQLite is the local default, PostgreSQL is supported via psycopg.
- Flask-Migrate/Alembic owns schema changes; the factory never runs `create_all()`.
- Flask-WTF provides validation and CSRF on every POST, including language selection and logout.
- Jinja templates, local CSS and vanilla JavaScript provide the interface. No frontend build pipeline, hosted fonts, stock photos or customer accounts.
- `app/content.py` centralizes paired English/Greek copy, choices, metadata and package configuration. `app/legal.py` contains both legal drafts.
- The session stores language, admin identity and an expiring opaque lead reference. It does not store enquiry contents or prefill name/email.
- Published future portfolio entries use translated JSON fields. The initial case study is an explicitly labeled technical capability outline; no client outcome is asserted.

See [PROJECT_MAP.md](PROJECT_MAP.md) for routes, models and workflows.

## Environment

| Variable | Purpose |
| --- | --- |
| `SECRET_KEY` | Private signing key, at least 32 characters in production |
| `DATABASE_URL` | Blank → `instance/site.db`; production `postgresql+psycopg://...` |
| `BASE_URL` | Canonical public origin, without path; HTTPS in production |
| `FLASK_ENV` | Explicit application switch: `development` or `production`; does not enable debug |
| `MAIL_ENABLED` | `false` by default; enables notifications only when explicitly true |
| `MAIL_PROVIDER` | Explicit `resend` or `smtp`; Railway Trial/Free/Hobby should use `resend` |
| `RESEND_API_KEY` | Private credential required for enabled Resend delivery |
| `RESEND_FROM_ADDRESS` | Verified Resend sender identity |
| `MAIL_ADDRESS` | Notification recipient; SMTP also uses it as sender/login |
| `MAIL_HOST`, `MAIL_PORT`, `MAIL_USE_TLS` | SMTP alternative settings; Gmail defaults to STARTTLS on 587 |
| `MAIL_APP_PASSWORD` | Private SMTP app password; only required with enabled SMTP |
| `CALENDLY_SCHEDULING_URL` | HTTPS `calendly.com` event link; blank until supplied |
| `RATELIMIT_STORAGE_URI` | `memory://` for one-process development; shared storage required in production |
| `TRUSTED_HOSTS` | Comma-separated production hostnames, required in production |

Existing process environment variables take precedence over `.env`. `postgres://` and `postgresql://` database URLs are normalized to the psycopg driver. Production refuses a missing/short key, non-HTTPS base URL, absent trusted hosts or in-memory rate-limit storage. Secure/HttpOnly/SameSite cookies and HSTS apply in production.

## Lead workflow and email

1. A visitor submits the short `/contact` brief with privacy acknowledgement.
2. Server-side validation and rate limits run; the lead is **committed before notification delivery**.
3. Notification uses the explicitly selected `MAIL_PROVIDER`. Resend uses its official HTTPS Python SDK with the configured sender, `MAIL_ADDRESS` recipient and validated client Reply-To. SMTP remains available for local development and eligible hosting. The message includes all brief fields and escapes HTML. Credentials and form contents are not logged.
4. Notification state becomes `sent`, `failed` or `disabled`; an interrupted notification-state write leaves `pending`. Check all non-sent states in admin.
5. The visitor receives the same success message whenever the initial save succeeded, then reaches `/book-call`. Database failure produces an honest error and does not send email.

SMTP is synchronous with a 10-second socket timeout. It is not a durable mail queue: a process crash can leave a `pending` notification, and failed emails are not automatically retried. Admin is the authoritative lead inbox. A future job queue/outbox can add delivery retries without changing lead persistence. After POST, a redirect prevents browser refresh from resubmitting the form; multiple deliberate submissions can create separate leads.

For local Gmail SMTP, configure an eligible account with two-step verification and an app password in the local `.env`. Do not use or disclose the normal account password. STARTTLS and certificate verification are enabled; cleartext SMTP authentication is rejected. Railway Trial/Free/Hobby production should use `MAIL_PROVIDER=resend`; see [RAILWAY_DEPLOYMENT.md](RAILWAY_DEPLOYMENT.md) for the required service variables and smoke test.

```powershell
.\.venv\Scripts\python.exe -m flask --app wsgi mail-smoke-test
```

This explicitly sends a harmless test using the selected provider, never displays credentials, and fails safely when disabled/misconfigured. Do not run it against production unless you intend to send the test email. Automated tests mock both transports. See [Google's app-password guidance](https://support.google.com/accounts/answer/185833).

## Calendly

Set `CALENDLY_SCHEDULING_URL` to your actual HTTPS Calendly event URL. No scheduling URL or credentials are hardcoded. A blank configuration shows email/phone alternatives.

Both paths work:

- Public page → `/book-call` → open inline calendar.
- Public page → `/contact` → saved brief → `/book-call` → calendar with name/email prefill.

No customer account or brief is required to book. Calendly assets are loaded only after the visitor clicks “Open booking calendar”; a direct external link is also provided. Name/email prefill is retrieved server-side for that visitor using a session-bound opaque identifier, valid for 30 minutes. It is not placed in the URL. The booking response is `no-store`, uses a no-referrer policy and is excluded from indexing. No booking webhook or confirmation synchronization is implemented; bookings remain managed in Calendly. See [Calendly's embed documentation](https://developer.calendly.com/api-docs/overview/embedding/recipes).

## Admin

`/admin` shows total/new/contacted/qualified/won counts. `/admin/leads` is paginated (25 rows); lead details show submitted data, UTC timestamps, privacy acknowledgement, delivery state, status and notes. Status and notes each use protected POST forms. Status values: `new`, `contacted`, `qualified`, `won`, `lost`, `archived`. First transition to contacted records `contacted_at`. Archiving is not deletion. No bulk export or public lead-detail endpoint exists.

## Production preparation — no deployment in this phase

1. Review and complete legal/business details, tax wording, retention periods and processor agreements in `app/legal.py`. The drafts are **not legal advice**. No analytics tracker is installed. If adding analytics, implement the required privacy/consent behavior before loading it. Legal draft references: [European Commission data protection principles](https://commission.europa.eu/law/law-topic/data-protection/information-business-and-organisations/principles-gdpr_en) and [individuals' rights](https://commission.europa.eu/law/law-topic/data-protection/information-individuals_en).
2. Use a fresh PostgreSQL database with least-privilege credentials, verified TLS to the database and restricted network access. Set `FLASK_ENV=production`, an HTTPS `BASE_URL`, `TRUSTED_HOSTS` and a strong secret through the hosting secret manager. Never copy development admins or test data.
3. Configure shared limiter storage using a protected `redis://`/`rediss://` URI; the Redis client is included in requirements. Memory storage is development-only.
4. Run migrations as a controlled release step and create the real admin using the hidden CLI prompt. Test PostgreSQL migration behavior in staging; this phase validates SQLite locally.
5. Run a production WSGI server, e.g. `.\.venv\Scripts\waitress-serve.exe --listen=127.0.0.1:8000 wsgi:app`, behind an HTTPS reverse proxy. Never expose Flask's development server. Debug is disabled by default; never use `--debug` in production.
6. Configure trusted proxy handling at the server/proxy layer so scheme and client IP are correct. Do **not** blindly trust client-supplied `X-Forwarded-*` headers. Without correct proxy configuration, rate limits may group users under the proxy IP. Restrict backend access to the trusted proxy.
7. Configure domain/DNS, SMTP and Calendly; verify both real conversion paths and accessibility on real mobile devices in staging. Booking-specific CSS permits inline styles for the provider, but scripts use nonces/host restrictions. Recheck CSP against the real embed.
8. Set up encrypted backups, restore exercises, uptime/error monitoring, dependency patching, log retention and a lead review/deletion process. Avoid form contents in proxy/APM logs. Establish support scope and incident handling.

Security controls include password hashing, CSRF, allowlisted redirects, bounded input, ORM parameterization, secure production cookies, request size limits, login/contact throttling, escaped templates/mail, CSP, clickjacking protection and no public sequential lead IDs. The default browser session is signed, not encrypted. No payment processing, health records, confidential case files or financial-account data is collected by this site. These require a separately designed system if added later. See [Flask security guidance](https://flask.palletsprojects.com/en/stable/web-security/).

Recommended next step: review the copy and legal/business placeholders, supply the real Calendly event, configure SMTP privately, then run a staging acceptance check before planning deployment.

## PRODUCTION DEPLOYMENT CHECKLIST

Local staging: [verification report](STAGING_VERIFICATION.md), [ordered checklist](STAGING_CHECKLIST.md), and [environment inventory](PRODUCTION_ENVIRONMENT.md). Docker availability and live database/Redis results are recorded separately from offline tests.

Audit results and remaining launch blockers: [PRODUCTION_READINESS.md](PRODUCTION_READINESS.md).

1. Create a fresh PostgreSQL database with restricted network access, least-privilege credentials and verified TLS. Do not copy the local database or development admin. Test upgrade and restore on a disposable staging database first.
2. Inject `FLASK_ENV=production`, `FLASK_DEBUG=0`, a private random `SECRET_KEY` (32+ characters), `DATABASE_URL`, HTTPS `BASE_URL`, `TRUSTED_HOSTS`, and shared `RATELIMIT_STORAGE_URI` through the host environment. Production refuses SQLite and missing database configuration. Use `postgresql+psycopg://` and provider-specific TLS parameters (`sslmode=verify-full` and trusted CA as needed). Redis must be private/authenticated; use TLS for remote connections. Install `requirements.txt` in a clean environment and retain the tested resolved dependency versions for release reproducibility. Production skips automatic `.env` loading when `FLASK_ENV=production` is injected before startup; set `FLASK_SKIP_DOTENV=1` for production Flask CLI commands.
3. Take a pre-release database backup, then explicitly run `python -m flask --app wsgi db upgrade` once as a release step. Run `python -m flask --app wsgi db check`. App import never migrates or seeds data.
4. Run `python -m flask --app wsgi create-admin` and enter an admin email, then a strong password at the hidden confirmation prompt. Use the email as the login username. Password arguments are unsupported. Never run `seed-dev` in production.
5. Configure DNS and the canonical domain. `BASE_URL` is the public origin only, without a path/query; its hostname must be allowed by `TRUSTED_HOSTS`. Redirect alternate domains to the canonical domain at the edge.
6. Configure HTTPS and HTTP-to-HTTPS redirects at the reverse proxy. Bind the WSGI server privately. Configure trusted scheme/client-IP forwarding for the actual proxy topology; verify two different clients receive separate rate-limit buckets. This app does not blindly trust forwarded headers. Gunicorn's scheme handling alone does not restore the client's IP behind every proxy. Choose and verify host-specific trusted proxy middleware/server settings before launch. Secure CSRF POSTs must see HTTPS. HSTS includes subdomains, so verify their HTTPS support too.
7. Configure Gmail: `MAIL_ENABLED=true`, `MAIL_HOST=smtp.gmail.com`, `MAIL_PORT=587`, `MAIL_USE_TLS=true`, `MAIL_ADDRESS`, private `MAIL_APP_PASSWORD`. Use an app password for an eligible account, never the normal account password. An intentional live `mail-smoke-test` is a manual staging step.
8. Configure the actual `CALENDLY_SCHEDULING_URL=https://calendly.com/<account>/<event>`; complete its legal/provider review. Blank configuration intentionally shows contact alternatives.
9. Submit one identifiable test lead on staging over HTTPS. Confirm persistence, admin visibility and Gmail receipt. Confirm failed mail still leaves the saved lead. Remove test data under the agreed retention process.
10. Manually open Calendly from the booking page and after a lead submission. Verify prefill, mobile display and CSP in a real browser. Automated tests do not contact providers.
11. Test admin login, logout, notes/status changes, CSRF rejection and unauthenticated access. Verify cookies are Secure, HttpOnly and SameSite=Lax, and no development account works.
12. Schedule encrypted database backups and access-controlled off-site storage; define retention, recovery-point and recovery-time targets. Test restoration into an isolated database and record the result. Back up required configuration securely, never in Git. Archiving a lead does not delete it.
13. Monitor availability, 5xx/503 rates, database/Redis connectivity, SMTP failures and pending/failed notification states. Collect stderr logs with restricted access, rotation and retention. Application production exception logs omit exception messages and tracebacks to avoid private data; do not enable SQL echo or request-body/session/header capture in proxy/APM logs. Review deployment server logs too. SMTP is synchronous with a 10-second timeout and has no automatic retry queue.

Complete all bilingual legal placeholders before public launch. Review the actual staging URLs, sitemap, robots, canonical/hreflang metadata and external links. `pip check` checks dependency compatibility, not known security vulnerabilities; run a current advisory scan in the release environment and patch/retest findings.

Linux production start command (inside the installed virtual environment):

```sh
gunicorn --workers 2 --bind 127.0.0.1:8000 --timeout 60 --error-logfile - wsgi:app
```

Gunicorn is installed on Linux via a platform-marked dependency. Adjust worker count and database connection budget to hosting capacity (default pool: up to 15 connections per worker). Start it with a process supervisor/container restart policy behind the configured HTTPS proxy. Do not use `--preload`, Flask's development server or `--debug` for deployment.

Windows production alternative:

```powershell
.\.venv\Scripts\waitress-serve.exe --listen=127.0.0.1:8000 wsgi:app
```

This is a server start command, not complete proxy configuration. Follow [Flask production deployment guidance](https://flask.palletsprojects.com/en/stable/deploying/) and [trusted proxy guidance](https://flask.palletsprojects.com/en/stable/deploying/proxy_fix/) for the selected host. Database pooling uses pre-ping to detect stale connections; see [SQLAlchemy connection pooling](https://docs.sqlalchemy.org/en/20/core/pooling.html).
